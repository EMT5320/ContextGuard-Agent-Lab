## 浮浮酱的总体判断

**Verdict：Go, but revise scope before heavy implementation.**

这个项目当前最有价值的地方，是它不是又做一个普通 RAG demo，也不是单纯 guardrail 样例，而是试图把 **Agent kernel、MCP-style tool boundary、evidence-gated sensitive action、trace、eval、case card** 放在同一个小而完整的公开作品里。README 里已经把项目定位成一个面向 Agent 系统评测的 portfolio project，并强调 MCP-style 工具边界、evidence-gated tool execution、traceability 和 reproducible evaluation；这条主轴是对的。

从求职画像看，它补的短板也比较准：当前公开作品和公司经验已经覆盖多 Agent、安全护栏、RAG、后训练/eval infra、trace observability 等，但公开 artifact 里还缺 **标准协议边界、可评测 Agent kernel、RAG + Agent 策略评测、evidence-gated execution、workspace loop** 这些高频 Agent 岗位信号。项目简报里这几个缺口已经写得很清楚。

所以浮浮酱建议的最终项目愿景是：

> **ContextGuard Agent Lab 是一个小型、可复现、以评测为中心的 Agent workbench，用统一 CaseSpec 比较不同 Agent 策略在上下文获取、工具调用、敏感动作证据门控、失败修复和成本预算下的行为差异。**

更短的 README 首屏版本可以写成：

> **A reproducible agent-evaluation lab for governed tool use: same cases, multiple strategies, evidence gates, traces, metrics, and case cards.**

这样比 “MCP-native, evidence-governed agent evaluation workbench” 更稳一点，因为当前代码还没有真的实现 FastMCP adapter 或完整 MCP server。等 MCP adapter 跑通后，再把 “MCP-native” 放回主标题更安全喵～(=￣ω￣=)

## 当前设计最强的部分

第一，**作品组合分工很清楚**。背景快照把目标岗位分成 stable、upward、stretch、low priority，其中 stable 是 LLM application / Agent engineering / RAG-context engineering，upward 是 Agent algorithm / application strategy algorithm / Agent evaluation；这个分层很适合指导项目取舍。

第二，**项目主张有辨识度**。设计文档把主轴收敛为：

```text
Agent kernel + MCP-style tools + evidence policy + strategy ablation + trace/report/case cards
```

而且明确提醒 RAG 和 guardrails 应该服务于 Agent kernel / Agent eval，不应该喧宾夺主变成单独产品面。

第三，**claim contract 做得很好**。`05_claim_and_eval_contract.md` 已经把 allowed claims 和 required evidence 对齐，例如 minimal auditable Agent kernel 需要 AgentState、ToolCallTrace、RunRecord、unit tests、sample run；strategy comparison 需要同一 CaseSpec 下的 leaderboard；evidence-gated execution 需要 PolicyDecision trace 和 unsafe allow metric。 这个对求职项目很重要，因为面试官最常问的就是：“这个 claim 对应什么证据？”

第四，**当前实现方向是健康的**。`run_eval.py` 现在能用无外部依赖的 deterministic kernel 跑 sample benchmark，构造 retriever、ToolRegistry、EvidencePolicyEngine，然后输出 JSONL run records。 `generate_report.py` 也能把 run records 汇总成 Markdown report。 这比一开始就接复杂 LLM provider 更稳。

## 最大隐患，浮浮酱要认真指出来喵～(..•˘_˘•..)

**第一，MCP-native 目前有 claim gap。** 当前 `ToolRegistry` 的确做了结构化参数和结构化返回，也在注释里说明它 mirror an MCP-like boundary。 但这还不是 MCP-native。缺少至少三样东西：工具 schema / capability metadata、FastMCP server adapter、MCP client 可调用 demo。所以当前 README 更建议用 **MCP-style / MCP-compatible tool boundary**，等 Phase 4 实现 FastMCP adapter 再升级措辞。

**第二，strategy ablation 现在还不成立。** README 和设计文档列了 `react_agent`、`plan_execute_agent`、`reflective_agent`、`guarded_agent`、`context_budget_agent`。 但当前 `AgentKernel.run()` 基本按 `case_type` 分支执行，`strategy` 参数还没有真正改变 action selection、reflection、budget、policy timing 或 repair 行为。 如果继续这样，报告里即使显示 4 个 strategy，也会显得像“换名字跑同一套逻辑”。

**第三，toy code repair stub 不能公开展示成成功案例。** 当前 `toy_code_repair` 分支只是返回固定 repair plan，并直接 `success=True`，同时标记 `repair_loop_stub=True`。 设计阶段可以这样占位，但公开 sample report 里千万别让它看起来像真实修复成功。否则 coding-agent-like 这个信号会被面试官一击打穿，超痛喵～(>_<|||)

**第四，eval validity 是最容易被攻击的点。** 当前 sample cases 只有 RAG、sensitive action、toy code repair 各一条。 设计文档规划了 RAG QA、prompt injection、retrieval poisoning、sensitive action、toy code repair 等 case families。 这个方向对，但不要只追求 80-120 条数量。更重要的是 balanced cases、bad-case taxonomy、false block / unsafe allow 的对照组，以及能解释策略差异的 case card。

**第五，MCP 不是安全解决方案本身。** 外部研究里已经有人专门指出 MCP 工具生态存在 prompt injection、恶意工具调用、credential theft 等安全风险；另有 2026 年论文认为 MCP 标准化了 agent 调用外部工具的方式，但生产级安全还缺身份传播、工具预算、结构化错误语义等机制。([arXiv][1]) ([arXiv][2]) 这反而强化了项目价值：ContextGuard 不要说“用了 MCP 所以安全”，应该说“在 MCP-style 工具边界上评测 evidence gate、trace 和 policy decision”。

## 建议的项目最终范围

浮浮酱建议把范围拆成四层：**Must-have、Should-have、Stretch、Cut**。

**Must-have：**

* Unified `CaseSpec` + validation。
* `AgentStrategy` interface，至少 4 个真正可区分策略：react、plan_execute、guarded、reflective。
* `ToolSpec` + `ToolRegistry` + `ToolExecutor`。
* Retrieval tools：`search_docs`、`read_doc`、`verify_citation`。
* Sensitive tools：`export_data`、`delete_record`、`change_policy` mock actions，由 policy gate 统一拦截。
* Trace：`TraceEvent`、`ToolCallTrace`、`PolicyDecision`、`RunRecord`。
* Metrics：success、tool_calls、evidence_coverage、unsafe_allow、false_block、repair_success、cost_proxy、latency_proxy。
* Reports：strategy ablation、guardrail eval、case cards。
* 三张强 case card：RAG citation、sensitive action、code repair。

**Should-have：**

* Prompt injection + retrieval poisoning case family。
* 简化版 `context_budget_agent`。
* FastMCP adapter，把已有工具暴露成 MCP-compatible server。
* CI / smoke tests / fixture validation。

**Stretch：**

* A2A reviewer handoff。
* Hosted LLM planner。
* 真实开源 repo repair tasks。
* 更复杂的 cost-quality frontier 图表。

**Cut：**

* UI。
* 通用 RAG 平台。
* 企业级安全 claim。
* 完整 Codex / Claude Code 替代品。
* 大型 guardrail rule library。
* W1/W2 的 A2A。

这些 cut 和现有风险登记表是吻合的：文档已经把 RAG 平台化、Agent kernel 太浅、coding-agent slice 过大、eval validity 不足、README 过度 claim 等列为核心风险。

## 开发计划建议

当前 roadmap 已经分了 Phase 0 到 Phase 4：设计审稿、deterministic baseline、strategy ablation、workspace repair loop、MCP and case cards。  浮浮酱建议稍微重排成更工程化的闭环：

**Phase 0：Review freeze。**
锁定项目定位、must-have / stretch / cut、README claim wording。门槛是每个公开 claim 都能映射到 artifact。当前 review packet 已经要求 reviewer 挑战定位、差异化、eval validity、一个月可行性、Agent algorithm 面试价值。

**Phase 1：Contracts and deterministic baseline。**
先实现 `ToolSpec`、`AgentStrategy`、`TraceEvent`、`ToolExecutor`，让 `run_eval.py --strategies react,guarded` 能生成按 strategy 分组的 JSONL。

**Phase 2：Policy gate in ToolExecutor。**
把 EvidencePolicyEngine 从 case 分支逻辑下沉到 ToolExecutor。Agent 尝试调用 sensitive tool，ToolExecutor 先生成 PolicyDecision，再决定 allow/block/review。这样 evidence-gated execution 才是执行链路的一部分。

**Phase 3：Strategy ablation。**
让 react、plan_execute、guarded、reflective 至少在工具调用顺序、policy gate 时机、失败后 retry、context budget 上有差异。报告展示 success / safety / cost_proxy / tool_calls，不只展示总成功数。

**Phase 4：Case expansion and eval validity。**
先做 40-60 条高质量 cases，别急着冲 120 条。RAG、injection、poisoning、sensitive action 先形成对照组。每个 case family 都要能解释“这个 case 想证明什么”。

**Phase 5：Workspace repair loop。**
实现 bounded fixture：`read_file`、`search_repo`、`apply_patch`、`run_tests`。先做 8-12 个真实 patch/test cases，再冲 20+。每个 repair case 必须有 failing test、patch diff、rerun result、trace。

**Phase 6：Public packaging。**
README 首屏放：一句话定位、架构图、CLI、leaderboard 摘要、case card 摘要、honest boundary、claim -> evidence 表。当前 README 已经有 honest boundaries，明确不声明企业级安全、不做完整 coding agent、不用公司数据，这部分要保留。

## 最小惊艳 MVP

主人，浮浮酱觉得一个更现实、更强的 MVP 不是 “80-120 条 case 全做完”，而是：

```text
40-60 条高质量 cases
4 个真实可区分策略
policy gate 完整闭环
8-12 个真实 workspace repair cases
1 份 strategy ablation report
1 份 guardrail eval report
3 张 case cards
README 首屏 claim -> evidence 可跳转
```

完整目标再放到后续：

```text
80-120 条 cases
20+ code repair tasks
FastMCP adapter
context_budget_agent 完整版
A2A reviewer handoff
```

这个拆法更适合求职展示，因为面试官通常不会逐条读 120 个 case，但会看你是否能把一个 case 从 **CaseSpec -> plan -> tool call -> policy decision -> trace -> metric -> case card** 讲完整喵～φ(≧ω≦*)♪

## 浮浮酱最建议立刻改的 5 件事

1. README 主 claim 暂时从 **MCP-native** 改成 **MCP-style / MCP-compatible tool boundary**，等 FastMCP adapter 完成再升级。

2. 新增 `AgentStrategy` 接口，不要让 `strategy` 只是字符串参数。

3. 新增 `ToolSpec` 和 `ToolExecutor`，把 policy gate 放进工具执行层。

4. `toy_code_repair` 在真实 patch/test 前不要返回 `success=True`，避免公开报告出现“stub 成功”。

5. 报告从单表升级为 family-level + strategy-level，并加入 bad-case taxonomy。
