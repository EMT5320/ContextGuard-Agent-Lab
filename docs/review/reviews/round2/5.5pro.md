# Review: ContextGuard Agent Lab Revised Scope

日期：2026-06-09
对象：EMT5320/ContextGuard-Agent-Lab revised design docs and starter skeleton
结论：Go with focused implementation. The pivot is directionally strong, but the code skeleton and metadata must be aligned before public packaging.

## 1. Verdict

**Go / revise：Go, with implementation-gate revisions.**

新版方向明显优于旧版 `evidence-governed workbench`：项目已经从安全审计 / observability 叙事，转向更适合作为求职展示的 **MCP-compatible Agent Strategy Benchmark**。这个定位更能补齐公开作品中的 AgentStrategy、tool boundary、context budget、verification tradeoff、strategy ablation 等缺口。

当前主要问题不是愿景，而是 **docs 已经 pivot，code skeleton 和 package metadata 仍有旧主轴残留**。进入实现 sprint 前，应先完成一次 alignment commit，避免 README、pyproject、sample report、starter code 对外讲出不同故事。

## 2. Strongest Improvements

### 2.1 主线收窄成功

新版 README 将项目定义为 “MCP-compatible agent strategy benchmark”，并明确它比较不同策略在检索、工具调用、验证、反思、上下文预算上的行为差异。这个定位比旧版 MCP-native / evidence-governed 更稳，也更贴近 Agent 算法、Agent eval、Context Engineering 岗位。

### 2.2 与 Loomstead 的分工更清楚

新版文档明确：Loomstead 负责 Agent Behavior Observatory、trace provenance、counterfactual replay、audit failure-analysis；ContextGuard 负责标准化 AgentStrategy ablation、MCP-compatible tool boundary、context budget frontier。这个 portfolio 分工成立。

### 2.3 Claim contract 更健康

Allowed claims / disallowed claims 已经比较清楚，尤其是：

- `MCP-compatible` 需要 ToolSpec / ToolRegistry / ToolExecutor / structured trace 支撑。
- FastMCP adapter 只有实现并展示后才能升级 claim。
- 不声明 enterprise security、full coding agent、RAG framework superiority。

### 2.4 Eval plan 从“数量导向”转成“有效性导向”

MVP 20-30 条高质量 case，Full target 60-80 条，并要求正例、失败例、negative control、bad case taxonomy。这个比单纯追求 80-120 条 case 更适合一个月 portfolio sprint。

## 3. Biggest Remaining Risks

### R1. Strategy 仍可能变成 label-only

文档已经要求策略必须改变工具序列、验证时机、reflection 行为、budget 使用或 success outcome。但当前 starter code 仍是 `AgentKernel.run(case, strategy: str)`，根据 `case_type` 分支执行，`strategy` 主要是记录字段。

**建议：Phase 1 的第一项不是扩 case，而是实现真正的 `AgentStrategy` interface。**

最低可接受实现：

- `ReactStrategy`：search/read 后直接答。
- `PlanExecuteStrategy`：先计划 multi-hop，可能 read 多个 doc。
- `VerifyThenAnswerStrategy`：必须调用 support / citation verifier 后才能答。
- `ContextBudgetStrategy`：根据 BudgetSpec 选择 top_k、是否 read、是否 verify。

### R2. `context_budget_agent` 容易被做浅

如果它只是 “少调用工具”，会显得像节流开关，不像 Agent control policy。它至少要展示一个明确策略：在有限 context/tool budget 下选择 retrieval depth、read depth、verification threshold，并在报告里展示 success-cost frontier。

建议加入：

```text
BudgetSpec:
  max_tool_calls
  max_context_chars
  max_verification_calls
  cost_proxy_limit
```

并且报告同时展示：

- raw success rate
- success-conditioned cost
- budget violation rate
- Pareto frontier
- dominated strategy cases

### R3. MCP-compatible 仍需具体化

文档已经避免了 MCP-native 过度承诺，但 “MCP-compatible” 仍需要最小证据，否则会被认为是 label。

MVP 前建议至少实现：

- `ToolSpec.name`
- `ToolSpec.description`
- `ToolSpec.input_schema`
- `ToolSpec.output_schema`
- `ToolSpec.risk_level`
- `ToolSpec.side_effect`
- `ToolSpec.cost_estimate`
- `ToolSpec.mcp_exposure`
- `export_tool_manifest()` 输出 JSON manifest

FastMCP adapter 可以放 Phase 4，但 ToolSpec manifest 最好 Phase 1 就有。

### R4. Independent grader 必须尽快从文档落到代码

当前 starter kernel 仍在控制循环内判定 RAG success，并且 code repair stub 直接 success=True。这会削弱 eval validity。

建议拆出：

```text
benchmark/schema.py: CaseSpec / BudgetSpec / ExpectedOutcome / GraderSpec
eval/graders.py: grade_retrieval_qa / grade_support / grade_budget / grade_sensitive_action
eval/metrics.py: aggregate_by_strategy / aggregate_by_family
```

Agent 只产生 trajectory 和 final answer，Grader 再独立判定。

### R5. Sample report 现在会误导

当前 sample report 显示 3/3 success，并包含 toy code repair stub success。这与新版路线“coding fixture stretch”“starter skeleton not completed”有冲突。

建议立即处理：

- 删除或重生成 sample report。
- 将 `toy_code_repair` 从 default sample cases 移出 MVP quickstart。
- 或将 stub case 标记为 `success=false` / `status=stub_not_claimed`。
- README Quick Start 改为生成 “starter smoke report”，不要叫正式 evaluation report。

### R6. 文档中 MVP strategy 数量存在轻微不一致

Project brief 的 MVP success definition 写 4 个策略：react / plan_execute / verify_then_answer / context_budget。Kernel design 和 README 又列了 reflective。建议统一措辞：

- MVP：react / plan_execute / verify_then_answer / context_budget。
- Full target：reflective。
- Phase 5 / optional：reflective repair + coding fixture。

如果时间充足，也可以保留 reflective，但不要让它挤压 context_budget。

## 4. Recommended Final Scope

### Must-have

- `CaseSpec` + `BudgetSpec` + `ExpectedOutcome` + `GraderSpec`。
- `AgentStrategy` interface。
- 4 个 MVP 策略：react / plan_execute / verify_then_answer / context_budget。
- `ToolSpec` + `ToolRegistry` + `ToolExecutor`。
- Retrieval tools：search_docs / read_doc。
- Verification tools：verify_citation / check_answer_support。
- Independent grader。
- JSONL RunRecord + structured ToolCallTrace。
- 20-30 条高质量 cases。
- strategy leaderboard + by-family metrics + success-cost frontier。
- failure taxonomy + 3 个 case cards。

### Should-have

- Adversarial context negative controls。
- Tool manifest export，证明 MCP-compatible boundary 的具体形态。
- Minimal FastMCP adapter plan or demo for 2-3 tools。
- Resume bullets / README claim-evidence table。

### Stretch

- Reflective retry / repair。
- Small sensitive-action balanced family。
- 3-5 bounded coding fixture cases。
- Hosted LLM planner comparison。

### Cut

- A2A。
- Heavy UI。
- Generic RAG platform。
- Full coding agent。
- Large guardrail SDK。
- Enterprise security claims。

## 5. Suggested First 5 Commits

### Commit 1: public-claim alignment

- Update `pyproject.toml` description from old MCP-native / evidence-governed wording。
- Rename starter report wording to smoke report。
- Remove or mark toy code repair stub from public default quickstart。

### Commit 2: schema contracts

- Add `BudgetSpec`, `ExpectedOutcome`, `GraderSpec`, `ToolSpec`。
- Extend `RunRecord` with `family`, `budget`, `cost_proxy`, `context_chars_used`, `grader_result`。

### Commit 3: ToolExecutor

- Move tool execution through `ToolExecutor`。
- Record cost/context/latency per call。
- Keep sensitive policy decisions inside ToolExecutor only for sensitive/side-effectful tools。

### Commit 4: strategy interface

- Implement `AgentStrategy` protocol。
- Add react / plan_execute / verify_then_answer / context_budget classes。
- Change CLI to accept `--strategies react,plan_execute,verify_then_answer,context_budget`。

### Commit 5: independent grader + first nontrivial report

- Move success scoring into `eval/graders.py`。
- Add 8-10 seed cases with at least 2 designed failures。
- Generate a starter ablation report with per-strategy rows。

## 6. Open Questions To Resolve Before Sprint

1. Is `reflective_agent` MVP or Full target? Recommendation: Full target unless implementation is trivial after verifier exists。
2. Should sensitive action appear in MVP quickstart? Recommendation: only 1-2 smoke cases, not main report。
3. What exact formula defines `cost_proxy`? Recommendation: document it early even if simple。
4. What is the first flagship case card? Recommendation: adversarial context + verify_then_answer beats react, because it best demonstrates strategy value。
5. Should FastMCP adapter be implemented in MVP? Recommendation: no; ToolSpec manifest in MVP, FastMCP in Phase 4。

## 7. Final Recommendation

Continue with the revised direction. The pivot is strong and better aligned with the intended portfolio gap than the original evidence-governed workbench. The next sprint should avoid adding new surface area and instead make the benchmark spine real:

```text
same cases -> different strategies -> structured tool calls -> independent grading -> metrics -> ablation report
```

Once this loop works for 8-10 cases and at least 3 strategies, scaling to 20-30 cases will be worthwhile. Before that, expanding MCP, coding fixtures, or sensitive-action logic will dilute the project.
